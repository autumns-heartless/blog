到底构建了什么？

从“能渲染 Koa 页面”走向“可维护的多页 Vue 前端工程”：理解这个分支的关键，不是背 Webpack 配置，而是看清请求、模板、构建产物和浏览器如何接力。

一句话结论

这个分支为 Elpis 补上了一套后端路由驱动的多页 Vue 构建体系：文件系统中的每个 entry.<page>.js 是一个页面入口，Webpack 自动发现它们、打包脚本、生成同名 .tpl 模板；Koa 收到 /view/:page 时渲染对应模板；浏览器再加载该页面自己的前端资源。

最重要的边界：这不是单页 SPA，也不是 Vue 服务端渲染。页面骨架由 Koa + Nunjucks 输出，Vue 在浏览器中挂载到 #root，属于“后端路由 + 多个客户端 Vue 页面入口”的组合。

解决的开发问题

新增页面时不想手工维护一长串 Webpack entry、模板文件和构建清单。

解决的性能问题

多个页面不能各自重复携带 npm 依赖和共享业务代码，需要拆出 vendor、common、runtime。

解决的协作问题

所有 Vue 页面默认接入 Element Plus、Pinia、UnoCSS，入口不再各写各的初始化。

解决的反馈问题

开发时让 Webpack 常驻监听，并通过 HMR 通道把更新传给浏览器。

先建立问题感：改造前后分别是什么样

维度develop 中已有的能力feature/frontend-build 增加的能力
页面访问已有 Koa 路由和 Nunjucks 的 ctx.render。路由改为渲染 app/public/dist/entry.<page>.tpl，让模板与构建产物对接。
页面资源旧的 app/public/output 中有手工固定模板。从入口文件自动推导页面名、包名和模板名，不再维护固定页面清单。
前端工程还没有完整的 Vue 3 多页打包链路。处理 Vue、JS、CSS/Less、图片、字体，并配置路径别名。
运行方式启动 Koa 即可返回模板。本地开发需要 Koa 与 Webpack 开发服务器并行：一个负责页面 HTML，一个负责实时编译的前端资源。

因此，这个分支的本质不是“换了个打包工具”，而是为原本偏后端的 Elpis 增加了一层前端应用装配系统。

整体运行链路：一次访问如何到达 Vue 页面

把下面的流程读懂，后续所有配置都会有明确位置。

图 1：运行时与构建时并非两套互不相干的代码。.tpl 是两者的交接物。

路由匹配：app/router/view.js 把 /view/:page 交给 ViewController.renderPage。
模板渲染：控制器执行 ctx.render('dist/entry.' + page)，Nunjucks 从 app/public 下读取生成后的 .tpl。
浏览器加载：模板中由 HtmlWebpackPlugin 注入当前页面对应的 JS/CSS；Vue 的 boot 在 #root 上挂载组件。
为什么模板必须落盘：开发环境中 Webpack 的 JS 可以留在内存里，但 Koa 是另一个进程，不能读取 Webpack 的内存文件系统；所以 writeToDisk 只把 .tpl 写入磁盘。

按提交理解设计演进

这 6 个提交并不是无关功能的拼盘，它们按“先能构建，再能扩展，再能高效开发”的顺序堆起来。

1. 8506eec：搭建多页 Webpack 的骨架

新增 webpack.base.js、Vue/JS/CSS/Less/资源 loaders、别名和模板。关键变化是把 Koa 渲染目标从旧的 output/... 调整为 dist/...：构建输出成为后端可以消费的模板。

2. 2fbc04e：从“页面清单”升级为“约定发现”

通过 glob 扫描 app/pages/**/entry.*.js，每发现一个入口便新建一个 HtmlWebpackPlugin。这样新增页面遵从文件命名约定即可被构建系统识别。

3. 9f8bd7e：为多页面做代码分割

将 node_modules 归入 vendor，把被至少两个页面使用的业务模块归入 common，并抽出 webpack runtime。目标是减少重复下载，并让稳定依赖更容易命中浏览器缓存。

4. 39e8c0d：分离开发构建与生产构建

把共享规则放到 base，开发关注 source map 与快速反馈，生产关注清理、抽取 CSS、压缩与并发构建。这样环境差异集中表达，而不是在一份配置里散落条件判断。

5. 4e11e6c：补上 Webpack 开发服务器与 HMR 通道

用 Express 托管 webpack-dev-middleware 和 webpack-hot-middleware，并把 HMR client 加入每个页面 entry。文件变化后，compiler 增量构建并经 SSE 通道通知浏览器。

6. 16420c8：统一前端应用启动与常用基建

新增 boot.js，让每个页面只保留“引入根组件 + boot”的最小入口；同时接入 UnoCSS、Pinia、可选路由、HTTP 包装器和页面生成脚本。

核心配置拆解：配置项在系统里各负责什么

1. 自动入口与动态模板

// app/webpack/config/webpack.base.js（逻辑摘录）
glob.sync('./app/pages/**/entry.*.js').forEach((file) => {
  const entryName = path.basename(file, '.js'); // entry.page1
  pageEntries[entryName] = file;
  htmlWebpackPluginList.push(new HtmlWebpackPlugin({
    filename: './app/public/dist/' + entryName + '.tpl',
    template: './app/view/entry.tpl',
    chunks: [entryName],
  }));
});

这段代码把一个命名约定变成自动化：entry.page1.js 同时决定 entry 名、输出模板名和页面资源注入范围。新增 app/pages/order/entry.order.js 后，构建时就会得到 entry.order.tpl；访问 /view/order 时，Koa 的动态路由也能匹配它。

学习点：“约定优于配置”不是不写配置，而是把重复、可推导的信息藏进统一命名规则。这里的代价是页面命名必须和路由参数严格一致。

2. 模板到底做了两件什么事

app/view/entry.tpl 提供统一 HTML 外壳：包含 #root 挂载点，以及由 Nunjucks 注入的 name、env、options。HtmlWebpackPlugin 再基于每个 entry 将当前页面所需资源标签注入进去。

谁写入写入什么发生时机
Nunjucks{{ name }}、{{ env }}、{{ options }}用户请求页面时
HtmlWebpackPlugin指向入口、vendor、common、runtime 等 bundle 的标签Webpack 编译时

3. 为什么要 splitChunks + runtimeChunk

图 2：页面入口不是“最终只能有一个 JS 文件”。构建把不同变化频率的代码拆开，目的是更少的重复和更好的缓存命中。

开发环境：为什么需要两个进程，以及 HMR 如何工作

在 Windows 下，npm run dev 启动 Koa（默认服务端口由 Elpis Core 决定）；npm run build:dev 先构建 UnoCSS，再用 concurrently 同时启动 UnoCSS watch 与 Webpack 开发服务器（127.0.0.1:9002）。前者负责页面请求与 API，后者负责实时编译资源与 HMR。

图 3：HMR 不是 Koa 的能力，而是 Webpack compiler、HMR 客户端与 hot middleware 之间的开发协议。

开发服务器中的“内存”和“磁盘”

webpack-dev-middleware 默认将编译结果放在内存，速度更快；但本项目显式设置 writeToDisk: filePath => filePath.endsWith('.tpl')。这不是“把所有构建结果写回去”，而是有意识地只让后端进程必需的模板落盘。

这是整套设计最关键的胶水：一个进程中的内存产物，不能自动被另一个进程读取；.tpl 在这里充当后端和前端构建系统的文件边界。

生产构建：目标从“反馈快”变为“资源更适合上线”

build:prod 先运行 UnoCSS，再执行 app/webpack/prod.js。它复用 base 配置，但改变了资源处理策略。

生产配置为什么这样做对应文件
CleanWebpackPlugin构建前清空旧的 public/dist，避免模板引用陈旧哈希文件。app/webpack/config/webpack.prod.js
MiniCssExtractPlugin开发期用 style-loader 注入样式，生产期将 CSS 抽成可缓存资源。webpack.prod.js
CSSMinimizer + Terser压缩 CSS 与 JS；Terser 配置会移除 console 输出。webpack.prod.js
HappyPack尝试利用多核并行处理 JS/CSS 加载任务以缩短构建时间。webpack.prod.js
content/chunk hash文件内容改变后 URL 改变；内容未变时可使用缓存。webpack.base.js / webpack.prod.js
注意：“生产配置做得更多”不等于每项都必然带来收益。像 HappyPack 与旧版插件的兼容性、缓存收益及构建耗时，应在真实 CI/构建数据中验证，而不是仅凭配置名称断言。

统一入口：如何把每个页面写成最小单元

// app/pages/page1/entry.page1.js
import boot from '$pages/boot';
import page1 from './page1.vue';

boot(page1);

boot.js 集中完成四类初始化：createApp、Element Plus、Pinia、UnoCSS，并允许页面按需传入 routes 和第三方 libs。因此页面 entry 只需声明“我要启动哪个根组件”。

Vue Router

只有传入 routes 才创建路由器；使用 hash history，避免后端额外配置 history fallback。

Pinia

用单例 Pinia 作为应用插件。每个独立 Vue 页面会创建自己的 Vue app，但均按同一入口规则接入 store。

UnoCSS

CLI 扫描 app/pages/**/*.{vue,js} 输出 uno.generated.css，由 boot 统一导入。

页面脚手架

npm run create:page -- name 创建目录、entry 和最小 Vue 组件，继续强化入口命名约定。

HTTP 包装器承担了什么

app/pages/common/http.js 基于 Axios 抽出 GET/POST/PUT/DELETE 快捷方法，统一传递 query、data、timeout，并将后端的 success / code / message 响应约定映射为 Element Plus 的消息提示。它的价值是让页面组件少重复“组装请求”和“分支提示”的样板代码。

安全审查提示：app/pages/common/http.js 中的请求签名固定值被写进浏览器侧源码，任何打包后的前端资源都可被用户读取。它不能被当作密钥保护；如该值承担真实鉴权作用，应立即轮换，并将机密签名逻辑移到服务端。本文刻意未复述该值。

收束：把这套架构记成一句话

“后端按 URL 选择模板，Webpack 按入口生成模板和资源，浏览器按模板启动对应的 Vue 页面。”
记住这三段职责，你就能从容定位：新页面为何没被打包、模板为何找不到、资源为何 404、HMR 为何失效，以及一段 Webpack 配置究竟在服务哪一环。
